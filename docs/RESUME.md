## 简历条目

> **MemoCore：可评测的 Agent 长期记忆引擎**　Python · PyTorch · bge-m3 / bge-reranker · BM25 · SQLite · FastAPI · MCP · DeepSeek API
>
> - **设计**：调研 Mem0、Graphiti 等高星记忆项目讨论最多的 issue（垃圾记忆、时间盲、写入成本高、查不到出处），设计"原文为本、零 LLM 写入"的记忆引擎：原文永不改写，时间注释和向量只作为派生索引；答案必须引用原文轮次，96.3% 的回答带出处且准确率不降。
> - **检索**：混合检索（bge-m3 + BM25 补候选 + 伪相关反馈 + 交叉编码器精排）加写入时规则时间锚定，再针对"漏掉的证据 70%～80% 没进候选池"调研 LongMemEval、MemMachine 等做法，加入时间感知查询和说话人先验。LoCoMo 1,540 题同预算下证据召回 76.4% → 88.4%、多跳题 57.3% → 74.7%，0 次 LLM 调用；消融否决了 RRF 融合、上下文向量等看似合理的做法。
> - **评测**：300 题端到端配对 bootstrap 检验，比朴素检索准确率 +5.3 个点（p = 0.017），只用全量上下文 6.5% 的 token 达到其 91% 的准确率；跨模型盲审裁判一致率 80%、0 题偏松；量化出思考模型重答有 43% 的答案会变，据此停止在噪声底上调 prompt。
> - **工程**：封装为 MCP 服务和 REST 接口，SQLite 一条消息一行（删除时覆写磁盘）、多用户隔离；把 LoCoMo 5,882 轮逐条写入后检索 1,540 题，与评测系统逐题一致；重排动态合批让并发吞吐 +40%、p95 延迟 -25%，单请求延迟不变；把每次写入后的全量重建改为增量索引（写时复制，并发检索不受影响，分数逐位不变），2 万条记忆时写后即查 2.4 s → 0.32 s。
> - **成本**：按 DeepSeek 官方计费规则逐次记账（缓存命中、思考 token、高峰 / 低谷），开跑前预估花费、自动等低谷半价；审计发现输出几乎全是思考：只差思考开关的 300 题配对检验里作答关闭思考准确率不降（55.0% → 57.7%），花费 -41%、延迟 -46%；裁判关闭思考会把同一批答案从 55.0% 判成 67.3%，口径变了，因此不替换。

## 30 秒介绍

我做了一个给 Agent 用的长期记忆引擎。主流项目在写入时用 LLM 把对话加工成事实或图，这一步有损，社区反馈最多的就是垃圾记忆、时间错乱和查不到出处。我反过来保留原文，只加规则做的派生索引，把功夫放在检索上：在 LoCoMo 上同样的上下文预算，证据召回从 76% 提到 88%，端到端比朴素检索高 5.3 个点并且做了显著性检验。它能通过 MCP 直接接进 Claude Code，评测的读取路径和上线的是同一套代码。

## 2 分钟讲法

1. **问题**：调研 6 个高星记忆项目的 issue，痛点集中在 LLM 写入有损（垃圾记忆、时间错乱、删不干净、查不到出处）和评测复现不出来。
2. **方案**：原文为本、零 LLM 写入；读取靠混合检索加精排；答案引用原文编号。
3. **怎么证明**：先用不花钱的证据召回调检索，再用 300 题配对检验看端到端；用裁判盲审确认裁判不放水；把服务和评测用逐条回放对齐。
4. **数据驱动的取舍**（最值得展开）：
   - RRF 融合反而更差，改成 BM25 只补候选；
   - prompt 调到第三版碰到噪声底，转去查检索瓶颈；
   - 发现漏掉的证据大多没进候选池，于是加时间感知查询和说话人先验，否决上下文向量；
   - 估算出端到端复测最多只能多 7 题、低于噪声，省下一次评测。
5. **反思**：多跳题仍有约 1/4 证据召回不到；严格裁判偏严；下一步是实体索引和更强的作答模型。
