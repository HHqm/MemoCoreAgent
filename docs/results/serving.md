# 服务化与并发性能（2026-11-03）

`memocore serve` 启动 REST 接口（FastAPI，单个 uvicorn 进程），与 MCP 服务共用同一个 `MemoryStore`。下面的数字都在一台 RTX 5060 笔记本上测得，模型为 bge-m3 + bge-reranker-v2-m3（半精度），关闭所有缓存，不调用任何 LLM API。

## 瓶颈在哪

一次检索约 300 ms，几乎都花在交叉编码器重排上（每题约 78 对）；查询编码约 16 ms，BM25 和建索引都在毫秒级。并发时吞吐卡在 3.4 次/秒，延迟随并发线性增加，说明 GPU 推理是串行排队的。

两项微基准：

| 试验 | 结果 | 结论 |
|---|---|---|
| 8 次检索的重排对合成一次模型调用，对比分 8 次调用 | 1,440 ms → 1,032 ms（-28%） | 合批有效 |
| 合批时 batch_size 从 64 加到 128 / 256 | 反而更慢（1,163 / 1,344 ms） | GPU 已接近满载，保持 64 |
| 按文本长度排序后再送入模型，减少填充 | 254 ms → 251 ms；分数有约 0.001 的半精度误差 | 没有收益，没有采用 |

## 动态合批

`BatchingReranker` 把并发检索发来的重排请求放进一个队列，由后台线程把 3 ms 内到达的请求合成一次模型调用，再把分数分发回各自的请求。只有一个请求在等待时不等窗口，直接调用，所以单个请求的延迟不受影响。任何一次调用出错，所有等待它的请求都会收到这个错误，不会一直挂起。

合批会不会改变检索结果：半精度下同一对的分数会随同批的其他样本有 0.001 级的浮动。实测 4 个用户的 160 次检索，单独跑和并发 16 合批跑返回的轮次 160 / 160 完全相同，证据召回也相同。

经真实 HTTP 压测（4 个用户、2,080 轮记忆、160 次检索，每次 20 轮预算）：

| 并发 | 吞吐（不合批 → 合批） | p50 延迟 | p95 延迟 |
|---:|---:|---:|---:|
| 1 | 3.3 → 3.3 次/秒 | 306 → 308 ms | 341 → 342 ms |
| 8 | 3.5 → **4.5** 次/秒（+29%） | 2,252 → 1,764 ms | 2,625 → **1,991** ms（-24%） |
| 16 | 3.5 → **4.9** 次/秒（+40%） | 4,573 → 3,205 ms | 5,240 → **3,941** ms（-25%） |

写入：4 段对话共 2,080 轮，按会话分批经 HTTP 写入用了 15 秒，约 7 ms 一轮（含时间锚定、向量编码和落盘）。

## 再往上提

单卡上限约 5 次/秒，受交叉编码器的计算量限制。可选的方向和代价：

- **少重排一些候选**：第 4 轮实测重排候选从 50 降到 30，重排量少 25%，证据召回少 1.2 个点。
- **换更小的重排模型**：需要重新做检索消融确认召回。
- **多卡或多副本**：记忆库是 SQLite 文件，多副本需要换成共享存储。

## 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/users/{user}/memories` | 原样写入一批消息，返回每条的编号和时间注释 |
| GET | `/users/{user}/recall?query=&budget=` | 检索，返回可直接放进 prompt 的上下文和逐条记忆 |
| GET | `/users/{user}/memories?ids=D3:12,D5:2` | 按编号取回原文，核对引用 |
| DELETE | `/users/{user}/memories?ids=...` 或 `?everything=true` | 按编号删除，或删除这个用户的全部记忆 |
| GET | `/health` | 健康检查 |

接口文档自动生成在 `/docs`。设置环境变量 `MEMOCORE_SERVER_TOKEN` 后，每个请求都要带 `Authorization: Bearer <token>`；监听非本机地址时必须设置。
