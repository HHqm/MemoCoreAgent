# 评测方法：长期记忆引擎怎么对比、看什么指标、怎么优化

## 先说目标

记忆引擎要证明的只有一件事：**用远少于全量对话的上下文，答得不比全量差；并且在信息更新、时间推理、该拒答的场景里，比朴素检索更可靠。**

下面的对照对象、指标和优化，都是为了用数字回答这句话。

## 1. 和谁比：逐层对照

| 系统 | 给模型的上下文 | 回答什么问题 | 状态 |
|---|---|---|---|
| `no_memory` | 什么都不给 | 下限：不给记忆，光靠猜和常识能拿多少分（开放推理题尤其要看） | 已实现 |
| `full_context` | 整段对话（平均约 590 轮，约 1.6 万 token） | 上限：上下文装得下时，准确率和成本各是多少 | 已实现 |
| `naive_rag` | bge-m3 检索原始对话轮次，取 top 20 | 最朴素的检索方案，记忆引擎必须明显超过它 | 已实现 |
| `hybrid_rag` | 原始对话轮次上的向量召回 + BM25 补充候选 + 重排 + 写入时时间锚定（默认配置） | 不用 LLM 加工、只优化读取和零成本写入，能做到什么程度 | 已实现 |
| `memocore` | 抽取并整理后的记忆条目，加上同一套读取路径 | 完整引擎："写"环节的加工值多少 | 下一阶段 |
| Mem0（外部对照） | Mem0 开源版产出的记忆 | 和业界主流方案在同一口径下比较 | 下一阶段 |

**为什么要分这么多层**：相邻两层只差一个因素，两层的分差就是这个因素的贡献。

- `no_memory` → `naive_rag`：检索本身带来多少。
- `naive_rag` → `hybrid_rag`：读取路径的优化带来多少。
- `hybrid_rag` → `memocore`：写入时对记忆做加工带来多少。
- `memocore` 对 `full_context`：用多少成本换来多少准确率。

## 2. 控制变量

- 所有系统共用同一个回答模型和同一个 prompt，temperature 都是 0。prompt 的哈希会写进 `run.json`。
- 同一个裁判模型，同一套评分规则（rubric）。
- 同一个题集，抽样用同一个随机种子。
- 检索类系统都在**相同的上下文预算**（放进上下文的轮数）下比较。不然多塞一些上下文，召回自然就高了。
- `run.json` 记录本次运行的全部设置；设置一变就拒绝续跑，避免把不同口径的结果混在一起。

## 3. 看什么指标：四层

### 3.1 最终效果：答对没有（主指标）

| 指标 | 说明 |
|---|---|
| 严格裁判准确率（**主指标**） | 答案要覆盖标准答案的全部要点、不矛盾、不额外编造，时间粒度也要一致 |
| 宽松裁判准确率 | 口径接近多数论文。严格和宽松之间的差，就是分数里"靠裁判放水"的部分 |
| token F1 | 与 LoCoMo 官方脚本口径一致，方便对齐原论文。对措辞很敏感，只作参考 |
| 分题型 | single-hop、multi-hop、temporal、open-domain，以及可选的 adversarial（考拒答） |
| 95% 置信区间 | 按题做 bootstrap 重采样 2,000 次。1,540 道题时区间宽约 ±2.5 个点 |
| 配对对比 | `memocore compare` 按题配对，给出差值的置信区间和 p 值。区间跨过 0 时，不能说有提升 |
| 裁判可信度 | 盲抽 100 道 LLM 裁判判定的题，另行标注后计算一致率（`audit-export` / `audit-label` / `audit-score`）。已用 Claude 盲审：一致率 80%，裁判 0 题偏松、20 题偏严 |

### 3.2 检索：证据进没进上下文（诊断用，不花钱）

- **证据召回@预算**：标注的证据轮次，有多少比例进了上下文。
- **证据全部召回的题占比**：一道题的证据全进来才算，对多跳题更关键。
- **错误归因**：对答错的题分两类看。证据没召回，就该优化检索；证据召回了还答错，就该优化记忆的组织方式、prompt 或模型。

### 3.3 效率与成本

- 每题上下文 token，以及占全量上下文的比例。
- 命中前缀缓存的 token 数。
- 读取延迟 P50 / P95（检索加重排）。
- 记忆引擎的写入延迟和写入 token。
- 跑一次完整评测的总 token 和总费用。

### 3.4 写入质量（记忆引擎特有，下一阶段）

- 抽取：记忆条目的精确率和召回率，参考 HaluMem 的按操作评测。
- 更新：LongMemEval 中 knowledge-update 类题目的准确率。
- 时间：temporal 题准确率，以及相对时间（如"昨天"）换算成日期的正确率。
- 拒答：adversarial / abstention 类题目的准确率。
- 规模：记忆条目数、每段对话的写入成本。

## 4. 实验流程（按省额度的顺序）

1. **先免费调读取**：用 `retrieval-sweep` 和 `retrieval-ablation` 只算证据召回，不调用 LLM。
2. **小样本冒烟（50 题）**：只用来检查流程，比如有没有截断、裁判能不能解析、缓存有没有命中，**不用来比较效果**。50 题的置信区间宽约 ±14 个点，拿它比 prompt 好坏没有意义。
3. **子集配对对比（300 题）**：所有系统用同一批题，只开严格裁判，用 `compare` 报告差值、置信区间和 p 值。花费约为全量的 1/5，差异是否显著由配对检验来判断。
4. **免费的错误分析**：在已有结果上做错误归因、错误分类，找出明确的问题再改，不靠反复重跑。改完先用 `--qa-ids` 定向抽查几十道代表题（只看行为，不下结论），回答进缓存，正式对比时复用。
5. **全量只跑一次**：对结论确定的最终配置跑全量，并开宽松裁判。
6. **抽检裁判**：盲抽 100 题另行标注，计算一致率，并逐条分析分歧。
7. **存档**：每次运行的 `summary.md` 和 `run.json` 一起保存，任何数字都能复现。

省额度的机制：规则预判（拒答、精确匹配直接判）、默认只跑严格裁判、前缀缓存预热、按内容寻址的响应缓存、截断和解析失败的结果不进缓存，续跑时只重做这些。

## 5. 优化路线：每项优化都对应一个指标

| 优化 | 解决什么问题 | 看哪个指标 | 结果 |
|---|---|---|---|
| 单轮切块，预算 20 轮 | 在有限预算里装进最多有用信息 | 证据召回@预算 | 76.4%（只用约 3% 的对话） |
| 交叉编码器重排（50 个候选） | 排在最前面的结果准不准 | 证据召回@5/10/20 | +16.2 / +12.3 / +7.9 个点 |
| 向量 + BM25，RRF 融合 | 人名、地名、数字这类需要字面匹配的信息 | 证据召回 | **负收益**：20 轮时 -1.6，多跳题 -5.2 |
| BM25 改为只补充重排候选 | 字面匹配挤掉语义命中 | 证据召回、multi-hop | 20 轮时 86.4%（比 RRF 高 2.4），多跳题比 RRF 高 7.0 |
| 写入时时间锚定 | 相对时间（"昨天"、"上周"）没法直接回答 | temporal 答案可见率 | 36.1% → 70.4%，上下文只多 3.2% |
| 邻近轮扩展 | 指代（"那次"、"它"）和一问一答被切散 | 证据召回 | **负收益**：-0.7～-5.9 个点 |
| 每个会话限命中次数 | 多跳题的证据分散在不同会话 | multi-hop 全部召回占比 | 小幅负收益：-0.3～-1.7 个点 |
| 伪相关反馈（第二跳检索） | 多跳题的第二跳证据和问题本身不像，排在 60 名以后 | 证据召回、multi-hop | 20 轮时 86.4% → 87.5%，多跳题 69.8% → 73.9%；0 次 LLM 调用 |
| 作答 prompt v2（按错误归因加规则 + few-shot） | 答案太笼统或多带细节 | 严格准确率（300 题配对） | +1.3，p = 0.53，**不显著**：prompt 调优碰到噪声底 |
| 引用约束作答 v3 | 多答沾边内容；结果无法追溯 | 严格准确率、引用精确率 | 准确率持平（p = 1.0），96.3% 带引用，精确率 78.7%，100% 落在上下文内 |
| 时间感知查询（参照 LongMemEval） | 问题点名的时段里的证据进不了候选池 | 点名时间的 204 题证据召回 | 93.7% → 96.1%，整体 +0.3；0 次 LLM 调用 |
| 说话人先验（参照 MemMachine 的 "user:" 前缀） | 只点名一人的题，96% 证据是本人所说，候选池里却有约 29% 是另一人 | 证据召回 | 87.5% → 88.0%（与时间感知查询合计 88.4%），开放域 +1.1 |
| 上下文向量（参照 Contextual Retrieval，不用 LLM） | 回复轮单独编码找不到 | 证据召回 | **没有采用**：单跳 +1.2，但多跳、开放域下降；让重排也看上文时多跳 -6.7 |
| 重排候选加深（50 → 100） | 漏掉的证据排得太靠后 | 证据召回、每题重排对数 | +0.3 个点、重排量 +60%，**不值得**，保持 50 |
| 作答截断自动重试 | 思考模型偶尔把输出上限全用在推理上，返回空答案 | 截断条数 | 被截断时用双倍上限重试一次 |
| GPU 半精度、批量编码、向量缓存 | 评测和检索太慢 | 建索引耗时、单次检索延迟 | 建索引 143 s → 51 s，单次检索 16.8 ms → 0.8 ms |
| 事实抽取 + 新增/更新/删除决策 | 原始对话噪声多，新旧信息冲突 | 准确率、knowledge-update、token | 下一阶段 |
| 多跳问题分解（LLM，按需） | 伪相关反馈后多跳题仍有约 1/4 证据没召回 | multi-hop 证据召回与准确率 | 下一阶段 |
| 跨会话实体聚合（人物卡片） | 多跳题证据分散 | multi-hop 准确率 | 下一阶段 |
| 拒答校准 | 对抗题乱答 | adversarial 准确率 | 下一阶段 |

## 6. 怎么写进简历

### 原则

- 每一条都写成"问题 + 做法 + 量化结果"，而且每个数字都能用一条命令复现。
- 优先写**同口径对比**和**消融实验**，而不是孤零零的一个高分。
- 至少准备一个"实验结果推翻了直觉"的故事，这在面试里最加分。

### 现在就能写的（数字已实测）

> **MemoCore：可评测的 Agent 长期记忆引擎**（Python、PyTorch、bge-m3、bge-reranker、BM25、SQLite）
>
> - 调研 Mem0、Graphiti 等 6 个高星记忆项目讨论最多的 issue，归纳出垃圾记忆、时间盲、写入成本高、评测无法复现等痛点；据此设计"原文为本、零 LLM 写入"的记忆引擎。原文永不改写，派生信息只作为索引，每条上下文都能回溯到原始对话轮次。
> - 读取路径采用 bge-m3 向量召回、BM25 补充候选、伪相关反馈第二跳、时间感知查询、说话人先验、bge-reranker 精排。在 LoCoMo 1,540 题、同一上下文预算下，证据召回从 76.4% 提到 88.4%，多跳题从 57.3% 提到 74.7%；只用 1/4 的上下文（5 轮）就超过了朴素检索用 20 轮的召回。
> - 通过消融实验推翻直觉：BM25 与向量做 RRF 融合反而让召回下降 1.6 个点（多跳题 -5.2），原因是字面匹配挤掉了语义命中；改为"BM25 只补充重排候选"后，多跳题比融合方案高 7.0 个点。邻近轮扩展在同预算下同样是负收益。
> - 写入时用 20 余条规则把"昨天、上周、去年夏天"等相对时间按会话日期换算成具体日期，覆盖 8.3% 的对话轮。时间类问题的答案可见率从 36.1% 提到 70.4%，上下文只增加 3.2%；写入每轮约 77 µs，不调用 LLM。
> - 搭建可信评测框架：固定预算比较，严格、宽松双裁判加盲审抽检，bootstrap 置信区间与配对检验；LLM 响应、向量和重排分数全部内容寻址缓存，可断点续跑。GPU 半精度和批量编码把建索引从 143 s 降到 51 s，单次检索从 16.8 ms 降到 0.8 ms。

### 端到端结果（已实测，可直接写）

> - 在 LoCoMo 固定种子的 300 题上做端到端评测（deepseek-flash 作答，deepseek-v4-pro 严格裁判）。hybrid_rag 的准确率比朴素检索高 5.3 个点（55.0% 对 49.7%，配对 bootstrap 95% CI [+1.3, +9.3]，p = 0.017），只用全量上下文 6.5% 的 token，就达到其 91% 的准确率。
> - 通过错误归因定位瓶颈：hybrid_rag 答错的题中 68% 证据齐全，再细分为漏答要点 41%、多答细节 33%，说明下一步该优化作答而不是检索（后续盲审发现"多答细节"有一部分是裁判过严）。
> - 设计省额度的评测流程：规则预判与 LLM 裁判在 1,502 条判定上 100% 一致，可以省去大量裁判调用；前缀缓存预热让全量上下文的缓存命中率从 36% 提到 96%；用 300 题子集加配对检验替代全量评测，花费约为全量的 1/5。
> - 用数据决定优化方向：作答 prompt 按错误归因迭代后，配对检验显示差值只有 +1.3 个点（p = 0.53），判断已触及模型随机性的噪声底，随即停止调 prompt；又对比 full_context 定位剩余差距主要来自多跳题漏召回，排序分析显示漏掉的证据 18% 排在 60 名以后，加预算无效，于是加入伪相关反馈第二跳，多跳题证据召回 +4.1 个点，0 次 LLM 调用。
> - 实现带出处的回答：上下文每行带原文轮次编号，答案必须引用出处、无法引用的内容不许写。300 题配对检验准确率持平（p = 1.0），96.3% 的回答带引用，引用 100% 可在上下文中核对，对照人工标注的引用精确率 78.7%，回应了社区"查不到出处"的痛点。
> - 把评测过的读取路径封装成能直接接入 Agent 的记忆服务：SQLite 持久化、多用户隔离、MCP 接口（remember / recall / read_memories / forget）。原文、时间注释和向量同行存储、同一事务写入，删除时一起删并覆写磁盘上的内容。把 LoCoMo 的 5,882 轮逐条写入后检索 1,540 题，与评测系统的结果逐题一致；单条写入 26 ms，检索 295 ms（笔记本 GPU）。
> - 用另一家族模型（Claude）对 100 道 LLM 裁判判定的题做盲审，标注时看不到裁判结论和系统名：一致率 80%（95% CI 71%～87%，kappa 0.61）。20 道分歧全部是裁判偏严、0 道偏松，说明报告的准确率是保守下限；偏严集中在把无害的补充细节判为"越界"，且在上下文更丰富的系统上更明显，因此 hybrid 对朴素检索的领先没有被裁判放大。
> - 用"先定位瓶颈、再调研、再逐项实测"的方式做了五轮检索优化：先查清漏掉的证据有 70%～80% 根本没进重排候选池，再参照 LongMemEval、MemMachine、Mem0、Contextual Retrieval 等做法在 1,540 题上逐项消融。采用了时间感知查询（点名时间的题召回 93.7% → 96.1%）和说话人先验（整体 +0.5），否决了上下文向量（多跳最多 -6.7）和加深重排（+0.3 个点换 60% 计算量）；同时用免费的上限估算说明端到端复测最多只能多 7 题、低于噪声，省下了一次评测额度。
> - 审计 API 用量并按官方计费规则优化：每次调用记录缓存命中、思考 token 和调用时段，自动算出每次评测花多少钱（全部实验合计 ¥15～29），开跑前预估花费并提示低谷半价。审计发现输出 token 几乎全是思考、检索类提示词几乎不命中前缀缓存；约 ¥1 的小样本实测显示关闭思考让作答花费 -41%、延迟 -58%，裁判花费 -72%；重答实验显示思考模式下同一 prompt 有 43% 的答案会变，说明本地响应缓存是结果可复现的前提。

### 还没做、做完可以补充的

- 人工复核盲审的 20 道分歧题（约 3 分钟），把"跨模型一致率"升级为人工结论；对同样 100 题跑宽松裁判做对照（约 100 次调用）。
- 用现在的默认配置（v3 引用作答 + 伪相关反馈）复测 300 题端到端。伪相关反馈只让证据召回 +1.1 个点，预计端到端差值小于噪声，所以先没花这笔额度。
- 关闭思考的 300 题配对检验（作答和裁判各一次），确认准确率不降后再替换默认值，低谷时段约 ¥1～2。
- 用更强的作答模型（如 deepseek-v4-pro）复测，看"证据齐全却答错"能下降多少。

### 面试常被追问的问题

| 问题 | 回答要点 |
|---|---|
| 只看 LLM 裁判的一个分数不行吗？ | 裁判可能放水。原始 LoCoMo 裁判与人工的一致率只有 43.67%（LoCoMo-Refined 的报告），所以要同时报严格/宽松两套裁判，再做盲审抽检。实测严格裁判 0 题偏松、20 题偏严，报告的是保守下限 |
| 为什么要固定上下文预算再比较？ | 召回会随上下文长度单调上升。不固定预算，"多塞上下文"就会伪装成"检索更好" |
| 为什么用 RRF，不用加权求和？ | 向量相似度和 BM25 分数的量纲不同。RRF 只看排名，不需要校准，也没有权重要调 |
| 重排的成本怎么样？ | 笔记本 GPU 上每题 50 个候选约 200～300 ms，是读取延迟的主要来源。降本方向：只在向量检索不确定时才重排，或减少候选数（候选 20 时预算 5 轮的召回是 71.2%，候选 50 时是 75.5%） |
| 时间锚定为什么不用 LLM？ | 写入阶段每次调用 LLM 正是社区反馈的成本痛点。规则只做确定的换算（昨天 = 会话日期减一天），不会编出原文没有暗示的日期；原文保留，换算结果只是注释 |
| "答案可见率"可信吗？ | 它只是代理指标：标准答案的每个词都在上下文里，不等于模型一定答对。所以它只用来衡量时间锚定这类改动，最终结论仍以 LLM 裁判为准 |
| 证据召回高，准确率就一定高吗？ | 不一定，召回只是必要条件。所以要做错误归因，把"没找到"和"找到了没答对"分开看 |
| 两个系统差 1 个点，算提升吗？ | 看配对 bootstrap 差值的置信区间是否跨过 0。1,540 道题时，单个系统的区间宽约 ±2.5 个点 |
| prompt 改了三版都没显著提升，为什么不继续调？ | 每换一版都有 12～16 道题对错翻转，说明答案本身有随机性：DeepSeek 文档写明思考模式下 temperature 不生效，实测同一 prompt 重答 30 题有 13 题答案变了。继续调只会追着噪声跑，把偶然波动当成提升。正确做法是转向能用免费指标验证的方向（检索），或换更强的作答模型 |
| 抽查 30 题明明改好了 5～6 题，为什么 300 题上没体现？ | 抽查题是挑出来的错题，本身有"回归均值"效应，重答一次就可能变对；而且没被抽查的题里也会有回退。所以抽查只看行为对不对，结论一律以 300 题配对检验为准 |
| 引用精确率 78.7% 算高吗？ | LoCoMo 的证据标注不完整，模型引用了正确但没被标注的轮次也会算错，所以这是下限。更硬的指标是"引用落在上下文内 100%"，即没有编造编号 |
| 伪相关反馈会不会把检索带偏？ | 第二跳只往重排候选池里补新轮次，最终仍由交叉编码器按原问题打分，补进来的不相关轮次排不上去；8 种参数组合召回都提升 1.0～1.3 个点，说明不是调参调出来的 |
| 评测的系统和实际用的是同一套代码吗？ | 是。`MemoryStore` 读取时就是在存好的轮次上构建评测用的 `HybridRAGSystem`。为了证明这一点，`memory-replay` 把 LoCoMo 逐条写进记忆库再检索，1,540 题选出的轮次和评测系统逐题一致，召回小数点后全部相同 |
| 删除怎么保证删干净？ | 一条消息的原文、时间注释、向量存在同一行，删除就是删这一行；开启 SQLite `secure_delete`，被删内容在文件里被覆写，测试直接扫描数据库文件确认原文不在；MCP 服务不开磁盘缓存，不会在别处留副本；编号永不复用，旧引用不会指到新消息 |
| 每次写入后都重建索引，不慢吗？ | 向量直接从库里读，不重新编码；419 轮的对话重建只要几十毫秒，检索的大头是重排（约 300 ms）。单用户到几万轮以上时，换成增量的向量索引（如 HNSW） |
| 为什么先做 MCP，不先做 REST？ | MCP 是 Agent 接工具的通用协议，Claude Code、Claude Desktop 等客户端加一条配置就能用；REST 接口在路线图里，核心逻辑都在 `MemoryStore`，加一层很薄 |
| 为什么不给 Agent 一键清空的工具？ | 删除不可逆。Agent 只能按编号删具体消息，清空整个用户要走库函数或命令行，由人来做 |
| 裁判一致率是人标的吗？ | 不是，是用 Claude 做的跨模型盲审：逐题标注时看不到裁判结论和系统名，标签文件里也记录了标注者。两个 LLM 一致不等于人工一致，所以 20 道分歧题全部公开，人工复核只要看这 20 题 |
| 严格裁判偏严，会不会让对比结论失真？ | 偏严只会压低绝对分数，不会放水；而且偏严在 hybrid、full_context 上比 naive 更明显，所以 hybrid 对 naive 的领先更可能被低估。真正要警惕的是偏松，这次 0 题 |
| Mem0 在 LoCoMo 上报 92.5%，你只有 55%，差在哪？ | 口径不同，不能直接比。Mem0 的裁判把"列表答对一项""日期差 14 天以内"都算对，本项目的严格裁判要求列全、日期粒度一致，盲审还显示它只偏严不偏松；回答模型也不同（gpt-4o 级别对 deepseek-flash）。能比的是同一口径下的相对提升，比如同预算下证据召回 76.4% → 88.4% |
| 为什么上下文向量（Contextual Retrieval）在你这里没用？ | 文档检索里片段之间重叠少，补上下文是纯收益；对话里相邻轮本来就在说同一件事，把上一轮复制进下一轮后两轮变得很像，在候选池和预算里互相挤占。多跳题需要多条不同的证据，受害最大（让重排也看上文时 -6.7）。所以只保留为选项 |
| 为什么不用 LLM 把多跳题拆成子问题？ | 先查数据：漏掉的证据大多排在向量 160 名以后，是召回源头的问题；再看文献：MemMachine 的检索 Agent（拆题、多轮改写）在 LoCoMo 上只比单次检索多 0.5 个点。花额度的收益太低，优先做免费的召回源头改进 |
| 说话人先验会不会把另一个人说的证据过滤掉？ | 不会，它只给相似度加 0.1，不做过滤；另一人的发言仍可以经 BM25 和伪相关反馈进入候选。只点名一个人的题里，另一人说的证据共 83 条，加分前找回 38 条、加分后 37 条，只少 1 条；点名者自己说的 1,964 条证据则多找回 13 条 |
| 跑一次评测要多少钱？怎么省？ | 一次 300 题的系统评测约 ¥1.3～3.3，全部实验合计 ¥15～29，每次调用都有记录。钱主要花在输出上，而输出几乎全是思考：作答关闭思考可省 41%，裁判可省 72%；其次是低谷时段半价；把提示词里固定的部分放在最前面能命中前缀缓存，但对检索类系统只省约 4% |
| temperature 设成 0，为什么结果还会变？ | DeepSeek 的思考模式不支持 temperature，设了也不生效。实测同一 prompt 重答，思考模式下 43% 的答案会变，关闭思考后仍有 23%。所以每次调用的结果都缓存下来，重跑时直接复用；比较两个版本时用配对检验，并把噪声底算进去 |
